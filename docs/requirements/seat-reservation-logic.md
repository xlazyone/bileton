**Описание логики блокировки мест при одновременном бронировании**  
**Модуль:** Схема зала и бронирование (Спринт 3, пакет 5.1)  
**Связанные пакеты:** 5.2 (схема БД), 5.3 (API POST /bookings с SELECT FOR UPDATE), 5.4 (верстка схемы зала), 5.5 (интеграция, обработка HTTP 409), 5.6 (нагрузочный тест), 5.7 (прогон сценариев, откат транзакции).

**1\. Цель и область**  
Задача \- исключить двойную продажу одного и того же места на одном сеансе при одновременных (конкурентных) запросах на бронирование, при этом не блокируя бронирование разных мест и не создавая искусственных задержек для пользователей.  
Область: только этап бронирования (создание записи о резерве). Оплата, генерация QR и валидация билета \- вне области пакета 5.1, но логика таймаута и статусов с ними согласуется (пакеты 6.3, 6.9).

**2\. Объект блокировки и гранулярность**

* Единица блокировки \- конкретное место на конкретном сеансе, то есть пара (session\_id, seat\_id).  
* Блокируется не весь сеанс и не весь зал: два пользователя, бронирующие разные места одного сеанса, не должны мешать друг другу.  
* Блокировка реализуется на уровне строки в БД через SELECT ... FOR UPDATE (пакет 5.3), а не через внешние блокировки (Redis, файловые локи) \- это упрощает откат и не требует дополнительной инфраструктуры.  
* Для брони нескольких мест одним запросом блокировка берётся по каждому месту отдельно, в детерминированном порядке (см. раздел 6).

**3\. Статусная модель места**  
Место в рамках сеанса проходит следующие состояния:

| Статус | Значение | Кто/что переводит | Освобождается? |
| ----- | ----- | ----- | ----- |
| free | Свободно, доступно для брони | Исходное состояние; возврат по таймауту | \- |
| reserved | Забронировано, ожидает оплаты | Пользователь через POST /bookings | Да, по таймауту |
| paid | Оплачено, билет оформлен | Модуль оплаты (6.3) | Нет |
| used | Билет использован (проход по QR) | Панель контроллера (6.9) | Нет |
| cancelled | Бронь отменена пользователем/системой | Пользователь или фоновый процесс | Да → free |

**Допустимые переходы:**

* free → reserved \- успешное бронирование;  
* reserved → paid \- успешная оплата;  
* reserved → free \- истечение таймаута или отмена;  
* paid → used \- проход по QR;  
* paid → cancelled \- возврат (если предусмотрен бизнес-правилами, вне 5.1).

**Запрещённые переходы:**   
paid → reserved, used → free, reserved → paid без оплаты. Любая попытка \- ошибка на уровне API.  
**4\. Таймаут мягкой брони**

* Бронь в статусе reserved живёт ограниченное время \- TTL (предлагается 15 минут; значение фиксируется и передаётся в 6.3 и 6.9).  
* В записи брони хранится expires\_at \= created\_at \+ TTL.  
* По истечении expires\_at фоновый процесс (или ленивая проверка при чтении схемы зала) переводит бронь в cancelled, а место \- в free.  
* Освобождение должно быть идемпотентным: повторный запуск фонового процесса не должен ломать уже оплаченные брони.  
* Пока бронь активна (reserved, expires\_at в будущем), место считается занятым для всех остальных пользователей.

**5\. Поведение при конфликте**  
**Сценарий A. Два одновременных запроса на одно свободное место.**

* Оба запроса проходят проверку «место свободно» до начала транзакции \- это нормально.  
* Внутри транзакции первый запрос берёт SELECT ... FOR UPDATE на строку места и создаёт бронь, коммитит.  
* Второй запрос ждёт освобождения блокировки, затем видит, что место уже reserved, и получает HTTP 409 Conflict.  
* В БД остаётся ровно одна активная бронь.

**Сценарий B. Повторный запрос того же пользователя на то же место (двойной клик).**

* Запрос идемпотентен: если активная бронь этого пользователя на это место уже существует, возвращается она же (200/201 с тем же booking\_id), а не 409\. Это защищает UX от двойного нажатия кнопки.

**Сценарий C. Запрос на место, которое только что освободилось по таймауту.**

* Место снова free, бронь создаётся штатно. 

**Тело ошибки 409 (контракт согласуется с пакетом 5.5):**

* HTTP-код 409;  
* машиночитаемый код ошибки (например, SEAT\_ALREADY\_BOOKED);  
* seat\_id и session\_id, чтобы фронт подсветил конкретное место;  
* человекочитаемое сообщение для пользователя.

**6\. Транзакционная модель**

* **Уровень изоляции:** READ COMMITTED \- достаточен, так как конфликт разрешается явной блокировкой строки через SELECT ... FOR UPDATE, а не за счёт уровня изоляции.  
* **Порядок блокировок:** при брони нескольких мест блокировка берётся строго в порядке возрастания seat\_id (детерминированный порядок). Это исключает взаимные блокировки (дедлоки) при встречных запросах.  
* **Границы транзакции:** проверка доступности → блокировка → создание брони → коммит. Всё в одной транзакции; при любой ошибке \- ROLLBACK, частичных записей в bookings не остаётся.  
* **Длительность транзакции** минимальна: никаких внешних вызовов (платёжный шлюз, генерация QR) внутри транзакции бронирования \- они выносятся в пакеты 6.3/6.9.

**7\. Требования к схеме БД (передаются в пакет 5.2)**

* В таблице bookings \- поля: id, session\_id, seat\_id, user\_id, status, created\_at, expires\_at.  
* Уникальный индекс на (session\_id, seat\_id) среди активных броней (статусы reserved, paid) \- страховка поверх FOR UPDATE: даже при ошибке в логике БД не позволит создать дубль.  
* Индекс на expires\_at для эффективного поиска просроченных броней фоновым процессом.  
* Внешние ключи на sessions, seats, users с ограничениями целостности.

**8\. Сценарии для нагрузочного теста (передаются в пакет 5.6)**

| № | Сценарий | Ожидаемый результат |
| :---- | :---- | :---- |
| 1 | 2 параллельных запроса на одно место | ровно 1 успех, второй \- 409 |
| 2 | 10 параллельных запросов на одно место | ровно 1 успех, остальные \- 409 |
| 3 | Параллельные запросы на разные места | все успешны, блокировки не мешают |
| 4 | Повторный запрос того же пользователя на то же место | возвращается существующая бронь, без дубля |
| 5 | Бронь после истечения таймаута | место снова free, новая бронь успешна |
| 6 | Встречные запросы на несколько мест в разном порядке | дедлоков нет, все брони корректны |
| 7 | Проверка БД после серии тестов | нет дублей (session\_id, seat\_id) среди активных броней |
