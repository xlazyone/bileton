**Use Cases и критерии DoD для входа/регистрации**

**1\. Область и акторы**

Модуль: Авторизация и профиль (Спринт 1, пакет 3.1.1)  
Связанные пакеты: 3.2.1 (таблица users), 3.2.2 (JWT и роли), 3.3.1 (верстка), 3.3.2 (интеграция форм с API), 3.4.1 (чек-лист безопасности), 3.4.2 (прогон тестов).

Акторы:

* Гость — неавторизованный пользователь.

* Зритель — зарегистрированный пользователь с ролью viewer.

* Контроллер — зарегистрированный пользователь с ролью controller.

* Система — backend (API авторизации), фронтенд, БД users.

**2\. Use Cases**

**UC-01. Регистрация нового пользователя**

Актор: Гость  
Цель: создать учетную запись для последующей покупки билетов.  
Предусловия: пользователь не авторизован; доступна страница регистрации.  
Постусловия (успех): в таблице users создана запись с хешированным паролем и ролью по умолчанию (viewer); пользователь авторизован (получен JWT) либо перенаправлен на вход.

Основной сценарий:

1. Гость открывает страницу регистрации.

2. Вводит имя, email, пароль, подтверждение пароля.

3. Нажимает «Зарегистрироваться».

4. Система валидирует формат email, минимальную длину пароля (не менее 8 символов), совпадение паролей.

5. Система проверяет, что email не занят.

6. Система хеширует пароль и создает запись в users с ролью viewer.

7. Система возвращает успех и токен (или редирект на вход).

8. Пользователь попадает в личный кабинет / на страницу входа.

Альтернативные потоки:

* A1. Некорректный email — шаг 4: сообщение «Введите корректный email», форма не отправляется.

* A2. Пароль короче 8 символов — шаг 4: сообщение «Пароль должен содержать не менее 8 символов».

* A3. Пароли не совпадают — шаг 4: сообщение «Пароли не совпадают».

* A4. Email уже занят — шаг 5: сообщение «Пользователь с таким email уже существует», предложение перейти ко входу.

* A5. Ошибка сервера/сети — шаг 7: сообщение об ошибке, данные формы сохранены, повтор возможен.

**UC-02. Вход в систему**

Актор: Гость (зарегистрированный пользователь)  
Цель: получить доступ к защищенным разделам (личный кабинет, бронирование, панель контроллера).  
Предусловия: учетная запись существует; пользователь не авторизован.  
Постусловия (успех): выдан JWT; фронтенд сохранил токен; пользователь перенаправлен в соответствии с ролью.

Основной сценарий:

1. Гость открывает страницу входа.

2. Вводит email и пароль.

3. Нажимает «Войти».

4. Система находит пользователя по email и проверяет пароль.

5. Система формирует JWT с идентификатором и ролью пользователя.

6. Фронтенд сохраняет токен и перенаправляет: viewer → афиша/личный кабинет, controller → панель контроллера.

Альтернативные потоки:

* A1. Пустые поля — шаг 3: блокировка отправки, подсветка полей.

* A2. Неверный email или пароль — шаг 4: общее сообщение «Неверный email или пароль» (без раскрытия, что именно неверно).

* A3. Ошибка сервера/сети — шаг 6: сообщение об ошибке, повтор возможен.

**UC-03. Выход из системы**

Актор: Зритель / Контроллер  
Цель: завершить сессию.  
Предусловия: пользователь авторизован.  
Постусловия: токен удален на клиенте; доступ к защищенным страницам закрыт.

Основной сценарий:

1. Пользователь нажимает «Выйти».

2. Фронтенд удаляет сохраненный токен.

3. Пользователь перенаправляется на страницу входа/афиши.

Альтернативный поток:

* A1. Токен истек — при попытке действия система возвращает 401, фронтенд очищает токен и перенаправляет на вход.

**UC-04. Доступ к защищенному ресурсу (разграничение ролей)**

Актор: Зритель / Контроллер  
Цель: убедиться, что доступ выдается только согласно роли.  
Предусловия: пользователь авторизован, есть JWT.  
Постусловия: запрос выполнен или отклонен с корректным кодом.

Основной сценарий:

1. Пользователь открывает защищенную страницу.

2. Фронтенд прикладывает JWT к запросу.

3. Backend валидирует токен и проверяет роль.

4. При достаточных правах — ресурс отдается.

Альтернативные потоки:

* A1. Нет токена / токен невалиден — 401, редирект на вход.

* A2. Роль не подходит (например, viewer открывает панель контроллера) — 403, сообщение «Доступ запрещен».

**3\. Критерии Definition of Done (DoD)**

**3.1. DoD для UC-01 «Регистрация»**

* Форма содержит поля email, пароль, подтверждение пароля; все поля обязательны.  
* Клиентская валидация: формат email, длина пароля не менее 8 символов, совпадение паролей. Проверка сложности пароля (заглавные/цифры/спецсимволы) не выполняется.   
* Серверная валидация дублирует клиентскую (нельзя обойти через прямой запрос к API), включая правило «не менее 8 символов».  
* Пароль хранится только в виде хеша (bcrypt/argon2), в открытом виде не логируется.  
* Новый пользователь получает роль viewer по умолчанию.  
* При занятом email возвращается понятная ошибка (HTTP 409), без раскрытия лишних данных.  
* После успешной регистрации пользователь авторизован или перенаправлен на вход.  
* Написаны и проходят тесты: успешная регистрация, занятый email, пароль короче 8 символов, несовпадение паролей.  
* Проверено на макете Figma (пакет 3.3.1), верстка совпадает.

**3.2. DoD для UC-02 «Вход»**

* Форма входа содержит email и пароль; кнопка блокируется при пустых полях.  
* Неверные учетные данные дают единое сообщение «Неверный email или пароль» (HTTP 401).  
* При успехе выдается JWT с user\_id и role; срок жизни токена задан.  
* Фронтенд сохраняет токен и корректно перенаправляет по роли (viewer / controller).  
* Написаны и проходят тесты: успешный вход, неверный пароль, несуществующий email, пустые поля.  
* Токен не пишется в логи и не отображается в URL.

**3.3. DoD для UC-03 «Выход»**

* Кнопка «Выйти» доступна авторизованному пользователю.  
* После выхода токен удален, защищенные страницы недоступны.  
* Повторный заход на защищенную страницу без токена → редирект на вход.

**3.4. DoD для UC-04 «Разграничение ролей»**

* Запросы без токена / с истекшим токеном возвращают 401\.  
* Запросы с недостаточной ролью возвращают 403\.  
* viewer не имеет доступа к панели контроллера; controller имеет доступ к валидации билетов.  
* Написаны тесты на 401 и 403 для обеих ролей.

**3.5. Общие критерии (сквозные)**

* Все сценарии покрыты чек-листом тестирования безопасности (передается в пакет 3.4.1).  
* Ошибки API имеют единый формат ответа (код \+ сообщение).  
* Документация Use Cases приложена к задаче в Jira/Trello.  
* Проведена ревизия с \[PM/Backend\] и \[Frontend\] до старта реализации (3.2.2, 3.3.2).
